# InvoiceFlow — AI-assisted invoice processing MVP

A modular Streamlit application that takes a real invoice PDF or image, extracts invoice fields, validates them, matches a vendor and purchase order, checks duplicates, applies deterministic decision rules, and stores a run-level audit trail.

> **Important:** This is an AP triage and decision-support MVP. It does not initiate payments. REVIEW and REJECT decisions should be checked by an authorised AP user.

## What it does

- Accepts text PDFs, scanned PDFs and common image formats (PNG, JPG/JPEG, TIFF, BMP, WEBP).
- Extracts embedded PDF text first; uses Tesseract OCR when the document is scanned or text extraction is insufficient.
- Uses optional Gemini structured extraction for difficult layouts; falls back to local pattern-based extraction when no API key is configured or the model fails.
- Normalises dates, currency and amounts.
- Validates required fields and arithmetic consistency where line items are available.
- Matches explicit PO references first; otherwise scores vendor and amount similarity.
- Detects repeated vendor/invoice-number pairs and file fingerprints.
- Applies deterministic APPROVE / REVIEW / REJECT rules.
- Persists run history and the full processing trace in SQLite.
- Provides a Streamlit run view, dashboard, result JSON and audit history.

## 1. Prerequisites

- Python 3.10+
- Tesseract OCR installed separately for scanned documents.
- Your existing procurement CSVs (no sample data is generated by this repository).

### Install Tesseract

**Windows:** Install the Tesseract OCR engine (UB Mannheim builds are commonly used), then add its installation folder to PATH. If needed, set `TESSERACT_CMD` in your environment to the full executable path.

**Ubuntu/Debian:**
```bash
sudo apt-get update
sudo apt-get install -y tesseract-ocr
```

**macOS:**
```bash
brew install tesseract
```

## 2. Setup

```bash
git clone <your-repository-url>
cd invoice-processing-mvp

python -m venv .venv
# Windows:
.venv\Scripts\activate
# macOS/Linux:
source .venv/bin/activate

pip install -r requirements.txt
```

Copy `.env.example` to `.env` if you want to configure optional settings.

Put your existing files in `data/`:

- `data/vendors.csv`
- `data/purchase_orders.csv`
- `data/po_line_items.csv` (optional)

Expected columns:

| File | Columns |
|---|---|
| vendors.csv | vendor_id, vendor_name, approved, currency, payment_terms |
| purchase_orders.csv | po_number, vendor_id, vendor_name, po_date, currency, total_amount, status |
| po_line_items.csv | po_number, item_description, quantity, unit_price, tax_rate |

Column names are case-insensitive. Extra columns are ignored. `approved` accepts true/false, yes/no, 1/0 and approved/unapproved. PO status values such as open, approved, issued are treated as usable; closed/cancelled are not.

You can alternatively upload the CSVs in the Streamlit sidebar each time you open a session. Uploads take precedence over the local data folder.

## 3. Optional Gemini extraction

The core pipeline works without a paid API. For more robust interpretation of unusual layouts, you can optionally use a Gemini API key if your account has access to a free quota:

```env
GEMINI_API_KEY=your_key
GEMINI_MODEL=gemini-2.0-flash
USE_LLM=true
```

The application only sends extracted invoice text to the model, not the original document. If the model is unavailable, invalid or returns incomplete data, the local extraction result is used. Review the provider's current pricing, quotas and data terms before using real confidential invoices.

## 4. Run globally with Streamlit

From the repository root:

```bash
streamlit run app.py
```

Streamlit prints a local URL (usually `http://localhost:8501`). To make it reachable on your network:

```bash
streamlit run app.py --server.address 0.0.0.0
```

For a hosted demo, deploy the repository to Streamlit Community Cloud or another Python host, install Tesseract in the deployment environment, and configure secrets/environment variables. Do not commit `.env`, API keys, invoices or procurement CSVs.

## 5. Processing flow

```text
Invoice upload
    ↓
File validation + SHA-256 fingerprint
    ↓
PDF text extraction ── insufficient text? ──→ OCR
    ↓
Structured field extraction (Gemini optional; local fallback)
    ↓
Normalisation + validation
    ↓
Vendor resolution + PO matching
    ↓
Duplicate detection (history + current file)
    ↓
Deterministic decision engine
    ↓
SQLite audit record + explainable result
    ↓
Streamlit result / history dashboard
```

## 6. Decision rules and assumptions

| Outcome | MVP rule |
|---|---|
| APPROVE | Critical fields present; approved vendor; reliable PO match; amount within configured tolerance; no duplicate; PO is usable |
| REVIEW | Missing/ambiguous fields; no PO; uncertain match; amount variance exceeds tolerance; currency mismatch; arithmetic warning |
| REJECT | Confirmed duplicate; vendor explicitly unapproved |

The amount tolerance is configurable in the UI (default 2%). The comparison uses invoice grand total against PO header total. This is intentionally conservative: where a PO has multiple invoices/partial billing, the current MVP may route the invoice to REVIEW rather than infer remaining PO balance. That is safer than silently over-approving.

A vendor-name fuzzy match is a candidate, not proof of identity. Low-confidence matches are sent to REVIEW. The application does not treat missing information as zero.

## 7. Meaningful demo scenarios

Use your own prepared invoices and PO data to demonstrate:

1. **Happy path:** clean PDF, approved vendor, exact PO and total within tolerance → APPROVE.
2. **Scanned invoice:** image-only PDF or JPG → OCR path, then normal extraction and matching.
3. **Amount mismatch / missing PO:** variance shown with exact amount and percentage; missing or uncertain PO → REVIEW.
4. **Duplicate:** process the same invoice twice → second run flagged as duplicate and REJECT.

## 9. Known MVP limitations

- OCR quality depends on scan resolution, skew, handwriting and language. Tesseract is not a handwriting recognition system.
- Local extraction uses common invoice labels and regular expressions. Highly unusual layouts should use the optional LLM path and still be manually checked.
- Tax/line-item reconciliation is advisory when the invoice's line items can be parsed; bundled charges and complex tax structures may require REVIEW.
- PO header comparison does not yet maintain cumulative consumed PO value across partial invoices.
- Fuzzy PO inference is deliberately cautious; it does not auto-approve on a fuzzy match alone.
- Duplicate detection is based on vendor + invoice number and exact file fingerprint. Near-duplicate semantic detection is not implemented.

## Security note

For a real company deployment, add authentication, role-based access, encrypted storage, retention controls, malware scanning and a documented data-processing agreement. Do not expose the demo app publicly with real financial documents.
